**An opt-in input for parallel dispatches.** The live evaluation workflow kept every dispatch in one concurrency group, `live-eval`, so one run at a time, and a newer pending run cancelled an older one. The addendum to `council/records/2026-11-23-wave-2-close-meeting-1.md` (decision P2) lets the wave 2 re-measure batch run several trials at once, and the seventh addendum to `council/records/2026-11-17-g3-whole-flow-cases.md` (decision T3) lets the whole-flow timer run its slots two at a time. The workflow gains a boolean input `parallel`, default false. With it, a dispatch of `flow/axil-timer` runs in `live-eval-timer-on` or `live-eval-timer-off` by its `knowledge` input, so GitHub never runs two timer runs of one arm together, and a dispatch of a case that is neither `flow/` nor `firmware/` runs in a group of its own, `live-eval-run-<run id>`; without it, and for the register block, every other `flow/` case and every `firmware/` case, the group stays `live-eval`. The first step of the `replay` and `live-eval` jobs fails the run when `parallel` is asked for one of those cases, and the second fails every dispatch whose case is not written exactly as its ID, both before the checkout and before any step that reads the secret. The input is read only by the group and the first guard, never by an `env:` or a `run:` line, and the secret is read by the same two steps as before. No harness, tool definition, card or knowledge file changes; the fingerprints are unchanged, and the workflow group's digest moves.
