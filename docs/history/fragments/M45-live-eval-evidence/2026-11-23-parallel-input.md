**An opt-in input for parallel dispatches.** The live evaluation workflow kept every dispatch in one concurrency group, `live-eval`, so one run at a time, and a newer pending run cancelled an older one. The addendum to `council/records/2026-11-23-wave-2-close-meeting-1.md` (decision P2) lets the wave 2 re-measure batch run several trials at once. The workflow gains a boolean input `parallel`, default false. With it, a dispatch of a case that is neither `flow/` nor `firmware/` runs in a group of its own, `live-eval-run-<run id>`, so it is never queued behind another run and no run can cancel it; without it, and for every `flow/` and `firmware/` case, the group stays `live-eval`. The first step of the `replay` and `live-eval` jobs fails the run when `parallel` is asked for a `flow/` or `firmware/` case, before the checkout and before any step that reads the secret. The input is read only by the group and those two steps, never by an `env:` or a `run:` line, and the secret is read by the same two steps as before. No harness, tool definition, card or knowledge file changes; the fingerprints are unchanged, and the workflow group's digest moves.
