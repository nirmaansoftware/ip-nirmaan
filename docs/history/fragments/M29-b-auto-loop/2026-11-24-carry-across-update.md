**Passing verdicts carry across the loop's merge of main.** main's ruleset "main: two keys" has required up-to-date branches since 2026-11-23 (strict, after the hq item main-strict-checks), so each move of main made every open pull request behind, the loop merged main into it, and the verdict cache, keyed by the exact head and main commits, sent both keys and the Founder Proxy back to the start. A founder-class records pull request (ip#492, about 40 minutes of review) was restarted more than five times in three hours without merging. The loop now keeps the heads it asked GitHub to merge main into (state `update_from`), and the review (`carry_basis` in `scripts/pr_review.py`) carries a key's or the proxy's earlier verdict to the new head only when every commit in between is a GitHub update-branch merge of main onto a head the loop updated, the pull request's diff against its merge base is byte-identical to the one the reviewers got, and main's changes since touch none of the pull request's files and no review-control file (CONFIG `carry`). Only a pass carries; a fail, needs-founder or deferral is reviewed from scratch, fix rounds are unchanged, and CI is never carried: the carry is reached only once the required CI is green on the new head. The carried verdict is posted on the new head with a note naming the head and main it was reviewed on, and logged `carried` (or `carry-refused` with the failed conditions). The loop's header and docs/REVIEW_MECHANISM.md no longer say strict is off. Tests in `tests/test_pr_loop.py` run the real step: a carry for both keys and for the proxy, across two merges while CI ran, and none for an author's own merge, an author's commit after the loop's merge, a changed diff, main touching a file of the pull request or a review-control file, an earlier fail or needs-founder, a run by hand, or before CI is green.
